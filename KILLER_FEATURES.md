# Power Guardian

## Концепция проекта

**Power Guardian** — интеллектуальная розетка на базе Ujin OS, которая не просто включает и выключает нагрузку, а обнаруживает опасные режимы, автоматически защищает квартиру и объясняет каждое своё действие.

Основная демонстрационная цепочка:

```text
Розетка измеряет мощность
  → обнаруживает перегрузку или аномалию
  → отключает нагрузку
  → создаёт событие
  → объясняет причину
  → показывает предотвращённый риск и экономию
```

Проект рассчитан на демонстрацию за 24 часа. Первый MVP работает на эмуляторе Ujin, а физическая Wi‑Fi-розетка подключается позже через адаптер после определения её модели и протокола.

## Контекст хакатона

Задача хакатона — разработать пользовательские сценарии умных домов, зданий и комплексов на базе Ujin OS с использованием эмуляторов оборудования и устройств.

В папке `task/quattrocold` уже находятся:

- документация по API и протоколу Ujin;
- 9 семейств эмуляторов устройств;
- локальная веб-панель каждого устройства;
- публикация сигналов в Ujin;
- приём команд через HTTP, pull и WebSocket-контракты;
- генератор новых устройств;
- сценарии `если → то` через `autoscripts`;
- набор офлайн-тестов конечных автоматов и клиентов.

Главный незакрытый слой — пользовательский продукт поверх этого фундамента: устройство, сценарный движок, понятный dashboard и эффектный сквозной сценарий.

## Smart Plug как устройство Ujin OS

Умная розетка должна выглядеть для платформы как обычное Ujin-устройство с декларацией сигналов.

### Сигналы

| Сигнал | Группа | Назначение |
|---|---|---|
| `power_switch` | Возможность | Включить или выключить реле |
| `power_w` | Свойство | Текущая мощность |
| `energy_kwh` | Свойство | Накопленная энергия |
| `voltage` | Свойство | Напряжение сети |
| `current_a` | Свойство | Текущий ток |
| `power_limit_w` | Настройка | Безопасный лимит мощности |
| `auto_off_seconds` | Настройка | Таймер автоматического отключения |
| `overload_alarm` | Свойство | Состояние защиты от перегрузки |
| `anomaly` | Свойство | Обнаружена аномалия потребления |
| `reset_protection` | Возможность | Сбросить защиту и разрешить повторное включение |

### Физика эмулятора

- при включении нагрузка потребляет мощность;
- `energy_kwh` увеличивается на каждом тике;
- при превышении `power_limit_w` реле отключается;
- по `auto_off_seconds` выполняется автоматическое отключение;
- при перегрузке выставляются `overload_alarm=1` и событие защиты;
- повторное включение после аварии требует явного сброса защиты;
- все команды проходят через стандартный контракт эмулятора Ujin.

## Killer feature: Power Guardian

### 1. Автопилот безопасности

Розетка сама реагирует на опасное состояние:

1. обнаруживает перегрузку;
2. отключает нагрузку;
3. фиксирует причину и время;
4. показывает пользователю понятное объяснение;
5. блокирует повторное включение до подтверждения.

Пример сообщения:

> Розетка отключена: мощность 2400 Вт превысила установленный лимит 2000 Вт.

### 2. Объяснимый умный дом

Каждое автоматическое действие отображается как цепочка:

```text
Сигнал → Правило → Решение → Результат
```

Например:

```text
power_w = 2400 Вт
→ power_w > power_limit_w
→ power_switch = 0
→ нагрузка отключена, перегрев предотвращён
```

Это показывает жюри не только результат, но и логику системы.

### 3. Предпросмотр сценария

Перед включением правила dashboard показывает:

> При мощности выше 2000 Вт розетка отключится. В симуляции это произойдёт через 12 секунд.

Пользователь может сначала запустить сценарий в виртуальном режиме, а затем применить его к устройству.

### 4. Распознавание профиля нагрузки

По простым признакам потребления можно определить условный тип нагрузки:

- чайник;
- обогреватель;
- холодильник;
- телевизор;
- зарядное устройство;
- устройство в режиме ожидания.

Даже эвристическая классификация создаёт эффект интеллектуального продукта:

> Похоже на обогреватель. Рекомендуемый лимит: 2000 Вт.

### 5. Поиск энергопаразитов

Розетка находит длительное потребление в режиме ожидания:

> За ночь устройство потребило 0.18 кВт·ч. Рекомендуется отключать его после 23:00.

Для демо достаточно считать ночной интервал, среднюю мощность и потенциальную экономию.

### 6. Групповая защита квартиры

Несколько устройств работают как единая система:

- Power Guardian отключает аварийную розетку;
- счётчик показывает изменение общего потребления;
- вентиляция или другие нагрузки переводятся в экономичный режим;
- оператор видит связи между устройствами на одном экране.

Эта функция демонстрирует ценность платформы Ujin лучше, чем управление одной розеткой.

## Основной сценарий демо

Демо должно занимать 3–5 минут.

### Подготовка

Запустить эмулятор Smart Plug и dashboard. В интерфейсе заранее показать:

- текущее состояние розетки;
- мощность;
- накопленную энергию;
- лимит мощности;
- состояние защиты;
- журнал событий.

### Показ

1. Включить розетку через dashboard.
2. Показать рост `power_w` и `energy_kwh`.
3. Установить лимит, например 2000 Вт.
4. Запустить сценарий «Защита от перегрузки».
5. Смоделировать резкий рост нагрузки до 2400 Вт.
6. Показать автоматическое отключение.
7. Показать объяснение причины в журнале.
8. Показать предотвращённый риск и оценку экономии.
9. Сбросить защиту и включить розетку обратно только после подтверждения.

### Сценарий в формате Ujin

```text
если smart_plug.power_w > smart_plug.power_limit_w
то smart_plug.power_switch = 0
```

Дополнительное правило:

```text
если smart_plug.energy_kwh увеличивается слишком быстро
то smart_plug.power_switch = 0
```

## Локальная архитектура MVP

```text
Browser phone/tv (web frontend)
   ↓ HTTP API
Local Orchestrator
   ├── SmartPlug emulator
   ├── Scenario Engine
   ├── Event Journal
   └── UjinClient adapter
```

### Компоненты

- `SmartPlug` — устройство и физика нагрузки;
- `ScenarioEngine` — проверка условий и запуск действий;
- `EventJournal` — история сигналов, срабатываний и действий;
- `DashboardServer` — HTTP API и статические файлы интерфейса;
- `UjinAdapter` — публикация сигналов и отправка команд в Ujin.

Для MVP использовать Python standard library и vanilla JavaScript, чтобы не тратить время на сборку и внешние зависимости.

### Минимальные API

- `GET /api/state` — состояние всех устройств;
- `GET /api/declaration` — декларации сигналов;
- `GET /api/scenarios` — список сценариев;
- `POST /api/scenarios` — создать или обновить сценарий;
- `POST /api/scenarios/<id>/toggle` — включить или выключить сценарий;
- `POST /api/commands` — ручная команда устройству;
- `POST /api/demo/start` — запустить демо;
- `POST /api/demo/reset` — сбросить состояние;
- `GET /api/events` — журнал событий;
- `GET /` — dashboard.

### Формат сценария

```json
{
  "name": "Защита от перегрузки",
  "enabled": true,
  "when": {
    "device": "smart_plug_1",
    "signal": "power_w",
    "operator": ">",
    "value": 2000
  },
  "do": [
    {
      "device": "smart_plug_1",
      "signal": "power_switch",
      "value": 0
    }
  ]

```

## Подключение физической розетки

Точная модель розетки пока неизвестна, поэтому прошивать её вслепую нельзя.

Перед интеграцией определить:

- производителя и точную ревизию;
- чипсет: ESP8266, ESP32, BK7231, RTL или другой;
- наличие UART и OTA;
- локальный HTTP-, MQTT- или TCP-протокол;
- возможность читать мощность и энергию;
- возможность управлять реле без облака;
- электрическую изоляцию и безопасный режим работы.

Физическое устройство подключается через адаптер с единым интерфейсом:

```python
class SmartPlugAdapter:
    def read_state(self):
        ...

    def set_power(self, on: bool):
        ...

    def read_power(self):
        ...

    def read_energy(self):
        ...
```

Эмулятор и физическая розетка должны использовать одну и ту же модель сигналов Ujin. Тогда dashboard и сценарии не придётся переписывать.

## AI-интеграции и Telegram

Power Guardian расширяется единым control plane. Dashboard, Telegram и MCP не управляют эмуляторами напрямую: они вызывают один orchestrator, который владеет состоянием, сценариями, событиями и политиками безопасности.

### MCP для AI-агентов

MCP-сервер запускается локально через `stdio` и предоставляет агентам:

- состояние устройств;
- декларации сигналов;
- последние события;
- список сценариев;
- анализ энергопотребления;
- симуляцию сценариев без изменения состояния;
- создание подтверждаемого запроса на команду.

Опасные команды не выполняются одним вызовом. Сначала агент получает `confirmation_id`, затем отдельным вызовом подтверждает действие. MCP-адаптер находится в `app/mcp_server.py`.

### Telegram

Telegram работает через long polling и поддерживает:

- `/status`;
- `/events`;
- `/scenarios`;
- `/demo`;
- inline-подтверждение отключения и включения розетки;
- уведомления об авариях через общий event journal.

Доступ ограничивается `TELEGRAM_ALLOWED_CHAT_IDS`. Токен задаётся через `TELEGRAM_BOT_TOKEN`.

Запуск и примеры находятся в `README_AI.md`. Интеграции можно запускать без внешнего Ujin-стенда, поэтому они пригодны для надёжного демо.

### Web-каналы

Единый web frontend в `app/web/` раздаётся тем же control API и работает в двух режимах:

- `phone` — портретная раскладка для браузера телефона;
- `tv` — landscape-раскладка с крупными значениями, focus-state и управлением стрелками/Enter.

Frontend не содержит бизнес-логики: он опрашивает `/api/state`, `/api/events` и `/api/scenarios`, а изменения отправляет через preview/confirmation API. Поэтому браузер, Telegram и MCP видят одно и то же состояние orchestrator.

```text
Android Phone / Android TV / Browser / Telegram / MCP
                        ↓
                   Control API
                        ↓
                   Orchestrator
                        ↓
                    Smart Plug
```

Android WebView-обёртки для Phone и TV запланированы в `TODO.md` и будут использовать эти же URL `/web/?mode=phone` и `/web/?mode=tv`. До их реализации те же режимы доступны в браузере устройства.
