# TODO для агента: WebView-приложения Power Guardian

> Актуализация: frontend переведён на **React + Vite** по прямому запросу
> пользователя. Исходники — `frontend/src`, изображения — `frontend/public/images`,
> сборка — `npm run build`, результат — `app/web/dist`. Сохраняйте React и
> чёрный минималистичный интерфейс с React Bits. Упоминания vanilla HTML/CSS/JS
> в старых пунктах ниже описывают предыдущий этап и больше не являются требованием.
> Phone и TV используют один React frontend; `?mode=tv` сохраняется.

> Статус: задачи 1–3 и backend/frontend-часть задачи 6 выполнены. Android-приложения (задача 4), `ANDROID_BUILD.md` и Android-часть демонстрации отложены по решению пользователя. Прошивка физической розетки не входит в этот этап.

## Цель

Добавить к существующему Power Guardian единый web-интерфейс и две Android WebView-обёртки:

1. приложение для Android-телефона;
2. приложение для Android TV.

Оба приложения должны использовать один frontend и общий backend control plane. Бизнес-логика Smart Plug, сценариев, подтверждений и событий должна оставаться на сервере.

## Что уже есть

- `app/orchestrator.py` — состояние Smart Plug, сценарии, команды и события;
- `app/control_api.py` — локальный HTTP API;
- `app/run.py` — запуск control plane;
- `app/telegram_bot.py` — Telegram-интеграция;
- `app/mcp_server.py` — MCP-адаптер;
- `task/quattrocold/emulators/devices/smart_plug.py` — эмулятор розетки;
- `README_AI.md` — документация AI/Telegram-интеграций;
- `KILLER_FEATURES.md` — продуктовая концепция Power Guardian.

## Задача 1. Добавить web frontend

Создать каталог `app/web/`.

Добавить файлы:

- `app/web/index.html`;
- `app/web/style.css`;
- `app/web/app.js`.

Frontend должен:

- работать без React/Vue и внешнего CDN;
- использовать обычные HTML, CSS и JavaScript;
- получать состояние через `/api/state`;
- получать события через `/api/events`;
- получать сценарии через `/api/scenarios`;
- обновлять данные примерно раз в секунду;
- показывать состояние соединения;
- корректно работать на телефоне и телевизоре;
- использовать один источник состояния для всех экранов.

### Экран телефона

Показать:

- состояние реле;
- текущую мощность;
- накопленную энергию;
- лимит мощности;
- состояние защиты;
- кнопки включения и выключения;
- кнопку сброса защиты;
- кнопку запуска демо;
- список последних событий;
- список сценариев.

### Экран телевизора

Добавить режим `tv`, который отличается от phone-режима:

- landscape layout;
- крупные значения;
- крупные кнопки;
- видимый focus-state;
- управление стрелками и Enter;
- последние события на большом экране;
- крупное предупреждение при перегрузке;
- визуальная цепочка `сигнал → правило → действие`.

Режим выбирается URL-параметром:

```text
/web/?mode=phone
/web/?mode=tv
```

## Задача 2. Расширить control API

В `app/control_api.py` добавить раздачу статических файлов:

- `GET /web/` — frontend;
- `GET /web/index.html` — основной HTML;
- `GET /web/style.css` — стили;
- `GET /web/app.js` — JavaScript.

Добавить API:

- `GET /api/health` — `{ "status": "ok" }`;
- `GET /api/config` — базовая конфигурация frontend;
- существующий `GET /api/state` использовать для live-состояния;
- существующий `GET /api/events` использовать для журнала;
- существующий `GET /api/scenarios` использовать для сценариев.

Для статических файлов использовать безопасную проверку пути. Нельзя разрешать чтение произвольных файлов через URL.

Для WebView по локальной сети:

- поддержать запуск `python app/run.py --host 0.0.0.0 --port 8787`;
- не требовать отдельный frontend-сервер;
- вернуть корректные `Content-Type` для HTML, CSS и JS.

## Задача 3. Реализовать управление из frontend

Опасные команды должны использовать существующий двухфазный механизм:

1. frontend вызывает `POST /api/commands/preview`;
2. получает `confirmation_id`;
3. показывает пользователю подтверждение;
4. вызывает `POST /api/commands/<confirmation_id>/confirm`.

Для кнопок реализовать:

- включить розетку;
- выключить розетку;
- сбросить защиту;
- изменить лимит мощности;
- запустить демо;
- сбросить демо.

При истечении confirmation token показать понятное сообщение и запросить новую команду.

## Задача 4. Добавить Android WebView-проект

Создать каталог `android/` с двумя модулями:

- `android/phone`;
- `android/tv`.

Использовать:

- Kotlin;
- стандартный Android WebView;
- без обязательных сторонних UI-библиотек;
- общий подход к загрузке web frontend.

### Phone APK

- portrait по умолчанию;
- URL: `http://<backend-host>:8787/web/?mode=phone`;
- разрешить JavaScript;
- разрешить доступ к локальному HTTP backend;
- показать экран ошибки при отсутствии соединения;
- добавить кнопку повторной загрузки.

### TV APK

- landscape по умолчанию;
- URL: `http://<backend-host>:8787/web/?mode=tv`;
- включить TV-friendly focus navigation;
- разрешить JavaScript;
- разрешить доступ к локальному HTTP backend;
- показать экран ошибки при отсутствии соединения;
- добавить кнопку повторной загрузки.

Адрес backend не должен быть зашит как единственный неизменяемый production URL. Для MVP достаточно одного из вариантов:

- `BuildConfig.BASE_URL`;
- URL в `gradle.properties`;
- редактируемая настройка при первом запуске.

Выбрать `BuildConfig.BASE_URL` как реализацию по умолчанию.

Для локального демо использовать:

```text
http://<IP компьютера в Wi‑Fi>:8787/web/?mode=phone
http://<IP компьютера в Wi‑Fi>:8787/web/?mode=tv
```

В AndroidManifest добавить `INTERNET` и разрешить cleartext traffic только для MVP локальной сети.

## Сценарий приёмки

1. Запустить backend:

   ```bash
   python app/run.py --host 0.0.0.0 --port 8787
   ```

2. Открыть в браузере:

   ```text
   http://127.0.0.1:8787/web/?mode=phone
   http://127.0.0.1:8787/web/?mode=tv
   ```

3. Проверить, что состояние Smart Plug обновляется.
4. Нажать «Запустить перегрузку».
5. Убедиться, что реле отключилось.
6. Убедиться, что предупреждение появилось на обоих режимах.
7. Установить Phone APK.
8. Установить TV APK или запустить TV emulator.
9. Подключить оба устройства к одному backend.
10. Выполнить команду с телефона и увидеть результат на TV.
11. Проверить, что Telegram и MCP получают то же состояние через общий control plane.

## Критерии готовности

- web frontend запускается через существующий `app/run.py`;
- phone и tv режимы используют общий код;
- frontend не содержит отдельной логики устройств;
- опасные команды требуют подтверждения;
- backend доступен по LAN;
- Phone APK собирается;
- TV APK собирается;
- оба APK открывают правильный режим frontend;
- перегрузка отображается на телефоне и телевизоре;
- изменения состояния синхронны между browser, phone, TV, Telegram и MCP;
- все Python-тесты проходят;
- реальные токены и секреты не добавлены в репозиторий.

## Ограничения MVP

- не делать отдельную нативную бизнес-логику для Android;
- не добавлять публичный сервер и HTTPS-деплой;
- не использовать облачные push-уведомления;
- не переписывать orchestrator под Android;
- не подключать физическую Wi‑Fi-розетку в рамках этой задачи;
- не требовать Google Play публикации.
