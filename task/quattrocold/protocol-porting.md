# Гайд портирования протокола Ujin на другой язык (для жюри/команд, 15.10.2026)

> **Твой стенд: тест-ОАЭ** (API `https://api-uae-test.ujin.tech/api`). Все адреса в этом документе уже переведены на него; где осталось слово «preprod» (история прогонов) — читай «тест-ОАЭ». Устройства: команда запуска в брошюре (`--ust-auth`), dev-токен не нужен.

Минимальный набор, чтобы эмулятор на JS/Go/Java/… жил на платформе.
Эталон реализации — Python `emulators/` (ujin_client.py, ws_client.py, core.py).

## 1. Модель данных
- Устройство = `model` (имя модели) + `serialnumber` (число, выдаёт платформа)
  + `ext_guid` (строка, наша внешняя id).
- Сигнал = имя, значение (число/строка), доступ `r|rw|w`, control
  (`text|switch|graph|counter|list|range|button`…), группа (для людей):
  **Свойство (r) / Возможность (rw,w) / Настройка (пороги, таймеры)**.
  Декларация своего устройства — JSON вида `core.py:Signal.as_declaration()`.

## 2. Контракты (в порядке нужности)
1. **Создание**: POST `import_device/create-update-device/`
   (`device-token`, `model`, `title`, привязка `apartment_id` или path).
2. **Публикация значений**: POST JSON `import_device/group-update-device-signal/`
   (`?device-token=`, тело `{"data":[{"sn":<ext_guid>,"s":"<класс>_<имя>",
   "v":<число>,"c":"<класс>"}]}`).
3. **Приём команд**: три варианта —
   a) HTTP-сервер на `device_first_server` в формате
      `GET /?data={"recv":[{"command":"management","id":"<sn>","<signal>":<v>}]}`;
   b) pull: `bmsdevice/get-device-info` → `signal_task_value` (нужен mgmt≠r)
      или `devices/difference?dt=`;
   c) WebSocket (когда завели): auth `{"token","event":"authenticate","signals":true}`,
      команда `{"event":"setValue","devices":[{"id":uniq,"sn":<число>,
      "signals":[{"name","value"}]}]}`, эхо по `id`.

## 3. Минное поле (обязательно для любого порта)
1. `0` не проходит (`empty()` сервера) — шли `0.001` или жди обходной путь.
2. Новый сигнал: первый запрос коротким именем (создаёт словарь), второй —
   полным `<класс>_<имя>` (значение). В один шаг значение теряется.
3. Автословари `management='r'` — команда вниз не пройдёт, нужен довод rw.
4. `sn` в WS — число; `ext_guid` проходит санитайзер (без `- . , ! ? / + & #`).
5. Шлюз devices.php: параметр `token=`, не `user_token=`.
6. Значения только числовые для float-сигналов; строки — отдельный случай.
7. `c` в публикации = **класс модели устройства** (для хакатонной модели —
   `integrations_devices`), не произвольный префикс: ФУП `lupsl` ищет
   устройство по `ext_guid + класс` и при несовпадении молча пишет в пустоту
   (`error=0`, данных нет). Проверено 20.10 парой устройств.

## 4. Приёмка порта (что должно работать)
1. Устройство создалось, видно в `bmsdevice/get-devices`.
2. Сигналы публятся и видны в `get-device-info` (+ в панели signal-panel LIVE).
3. Команда вниз доходит хотя бы одним из трёх путей.
4. Есть декларация сигналов (JSON) с тремя группами.
5. README: как запустить за 3 команды.

## 5. Что согласовать (Виталий)
Список языков для официальных портов и кто что ведёт. Кандидаты: TypeScript
(node), Go, Java/Kotlin, C#. Ядро (FSM-хелперы) переносится механически —
`core.py` это ~250 строк.
